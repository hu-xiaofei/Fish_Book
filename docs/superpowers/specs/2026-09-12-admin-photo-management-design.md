# FishBook：管理员照片管理设计

状态：用户已在对话中批准首版范围；本文件将批准内容落成实现约束。尚未实现、迁移或部署。

## 1. 目标与边界

复用现有 `ADMIN`，增加所有用户照片的列表、用户筛选、预览、替换、删除和管理员操作记录。管理员删除的是照片，不是钓获记录；管理员不能借此修改钓获字段、收藏、账号或角色。

首版不提供旧照片恢复、审核状态、批量删除、新增角色、通知系统或公开图片链接。允许管理员因管理需要处理照片，并不授权开发期间操作真实业务照片。

## 2. 全局约束

- 复用现有 `USER`、`ADMIN`，不新增角色或第三方依赖。
- 普通用户只能读取、上传、替换和删除自己的照片；现有管理员通过独立管理接口查看、替换和删除所有用户的照片。
- OSS 和 MinIO 仍私有；不返回公开或预签名 URL、对象键、Bucket、Endpoint、凭证或 SDK 错误细节。
- 照片格式仍为 JPEG、PNG、WebP，最大 10 MiB；沿用服务端签名校验和存储大小上限。
- 写操作继续要求 Session、服务端角色/所有权校验和 CSRF；不能仅靠前端隐藏按钮授权。
- 所有照片上传、替换、删除都必须提供当前版本；旧版本冲突必须拒绝，不能自动刷新版本后重试写入。
- 成功的管理员替换/删除、照片引用更新和旧对象清理入队必须在同一数据库事务提交；事务失败不留下成功操作记录。
- 不提供旧照片恢复；旧对象继续通过清理补偿删除，不做前缀批量删除。
- 使用现有 Java 21、Spring Boot、MySQL 8.4、React、TypeScript 和 TanStack Query；不调整依赖版本。
- 本轮仅本地开发和测试，不执行云资源操作、真实数据库迁移、购买、发布、推送或合并。
- 保留用户现有文件和 MinIO 数据；已批准的学习型 RDS 内网非加密例外不扩展为浏览器或 OSS HTTPS 例外。

## 3. 授权与最小暴露

`/api/v1/admin/photos/**` 复用现有 `hasRole("ADMIN")`。应用服务再次通过当前登录邮箱查询数据库中有效的当前用户并确认 `role == ADMIN`，防止绕过 Web 边界或使用过期的角色缓存。

原 `/api/v1/catches/{id}/photo` 仍严格校验所属用户，管理员不通过这个用户接口绕过所有权。管理路径与用户路径共用内部存储/修改编排，不能共用一个未校验角色的任意记录读取入口。

管理列表只包含有照片的记录，展示记录 ID、所属用户 ID/昵称、鱼类名、钓获日期、照片是否存在、当前版本、更新时间。按所属用户 ID 筛选，不查询或暴露邮箱、详细钓点、笔记、账号状态或照片对象键。管理详情在照片删除后仍可显示该记录的无照片状态和历史操作；钓获记录本身不存在则返回 404。

## 4. 版本与并发

新增 `catch_records.version BIGINT NOT NULL DEFAULT 0`，用 JPA `@Version Long version` 管理整个钓获记录版本。版本覆盖照片和记录字段：即使只是钓获信息变化也保守地拒绝旧照片操作，这比静默覆盖更安全。

领域对象必须携带版本，`update`、`withPhotoObjectKey`、`withoutPhoto` 保留当前版本，不能在转换实体时重置为 0。新建对象版本为 null，由 JPA 插入为 0。原有构造/restore 的测试兼容入口可保留，但生产持久化必须读取真实版本。

用户详情和新建记录响应增加 `revision` 字符串，例如 `"0"`；管理列表/详情提供相同字段。字符串避免 JavaScript 数值精度损失。照片 GET 返回相同版本的强 ETag。

用户和管理员照片 PUT/DELETE 必须携带 `If-Match: "0"` 这样的单一、带双引号的非负十进制版本；不接受 `*`、弱 ETag、多值、负数或超出 Long 范围的值。无条件旧客户端不得静默放行。

照片 PUT 流程：授权 → 读取记录和比较请求版本 → 验证文件 → 上传新的 UUID 对象 → 数据库事务中重新读记录/比较版本 → `saveAndFlush` 以触发真实乐观锁检查 → 管理员操作记录（仅管理路径）和旧对象清理入队 → 提交。最后比较后仍发生竞态时，JPA 乐观锁失败同样返回冲突。失败后的新对象不成为业务引用，应做明确对象的删除补偿；删除失败可用新增 `UPLOAD_ROLLBACK` 原因入队，数据库也不可用时固定诊断并在手册记录残余孤儿风险，不隐藏原错误。

DELETE 在事务内比较版本，更新/flush、操作记录和清理入队原子提交。没有照片且版本一致时返回 204，不重复记录操作或重复入队；同一个旧版本重复请求可以返回冲突，这是有意的并发保护，不允许因此删除后来上传的新照片。

普通用户的钓获字段更新也必须保留并检查 JPA 版本。原生整条记录删除改为按 `id + userId + version` 条件删除：并发替换后不能依据旧对象键清理或删除新版记录。

## 5. API

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET | `/api/v1/admin/photos?userId=41&page=0&size=20` | 有照片记录分页；用户筛选可省略 |
| GET | `/api/v1/admin/photos/{recordId}` | 最小管理详情，含 `hasPhoto`、`revision` |
| GET | `/api/v1/admin/photos/{recordId}/content` | 经授权的照片字节 |
| PUT | `/api/v1/admin/photos/{recordId}/content` | multipart `photo` + If-Match，替换已有照片 |
| DELETE | `/api/v1/admin/photos/{recordId}/content` | If-Match，移除照片，保留记录 |
| GET | `/api/v1/admin/photos/{recordId}/operations?page=0&size=20` | 管理员操作分页 |

列表 page 为非负整数，size 默认 20，范围 1～50；userId/recordId 为正整数。非法查询固定 400，匿名 401，非管理员 403；用户路径的非所属记录仍是 404，不泄露存在性。管理员替换无照片记录返回 404，不扩大为上传新的照片。

无版本返回 428/`PHOTO_VERSION_REQUIRED`；非法版本返回 400/`INVALID_PHOTO_VERSION`；过期版本和写入竞态返回 409/`CATCH_PHOTO_CONFLICT`，固定中文提示“照片或记录已被修改，请刷新后重新确认操作”。不得将数据库/SDK 错误或对象键放入提示。存储不可用保留 503/`MEDIA_STORAGE_UNAVAILABLE` 和“媒体存储暂时不可用”。

管理图片和相关私有元数据响应使用 `Cache-Control: private, no-store`；图片保留 MIME、inline、nosniff，不支持共享缓存。用户图片也改为 no-store，并用当前 revision 更新图片地址查询参数，避免管理员修改后长期显示旧照片。未知异常不在本轮扩大为全局日志重构。

## 6. 管理员操作记录

新表 `admin_photo_operations` 保存：自增 ID、操作者用户 ID、所属用户 ID、钓获记录 ID、操作类型 `REPLACED`/`REMOVED`、修改前版本、操作时间。只记录通过管理路径成功提交的真实修改；用户自助操作、读取、失败、空照片重复删除不记成功日志。

不保存图片内容、原文件名、对象键、凭证、完整请求/异常、邮箱或不可控自由文本。标识字段不使用级联外键删除，钓获记录未来删除不抹掉已有操作证据。操作记录在应用中只读，不提供修改、删除或导出接口；不声称能够防止数据库管理员篡改。当前页面显示近期操作，按时间和 ID 倒序分页，不加入独立审计系统。

## 7. 前端

新增 `/admin/photos` 管理列表、`/admin/photos/:id` 管理详情，均复用 `AdminRoute`。管理员导航增加“照片管理”，非管理员不展示；通用拒绝提示不再仅称图鉴维护。

列表支持所属用户 ID 筛选、URL 分页、空状态、403、401 和加载重试；不在列表一次性加载所有大图，进入详情才预览图片。详情展示最小记录信息、原照片、新照片本地预览、替换按钮、删除确认和近期操作。切换目标、退出登录、401/403 时清空选择文件和对象 URL；本地预览 URL 使用 `URL.revokeObjectURL` 清理。

替换/删除确认绑定“记录 ID + 当前 revision + 文件（替换）”，确认期间版本变化应关闭确认并要求重新确认。请求进行中禁用相关控件；409 保留冲突提示、刷新元数据、不自动重试、不沿用旧确认写入。成功后重新获取详情、列表及操作记录；用户自己的照片缓存也失效。使用现有 sessionGeneration 防止退出登录后的迟到响应恢复私有内容。

用户端 `CatchPhotoPanel` 接收 revision；新建记录可选照片上传使用新建响应的 revision，失败重试先显式展示当前状态并重新确认，不用旧版本无限重试。提示统一为“你和平台管理员可查看，管理员可因管理需要替换或移除照片”。不改变用户上传/删除自己的照片能力。

## 8. 验收与发布边界

测试必须覆盖：迁移旧数据版本、JPA 乐观锁、版本条件整记录删除、管理员角色双重检查、匿名/USER 禁止管理、普通用户隔离、照片 MIME/大小、缺失/非法/过期版本、真实用户/管理员写入竞态、清理和操作记录事务回滚、新对象补偿、加载失败、确认后不自动重试、会话缓存清理、本地预览回收、旧照片不可恢复提示。

完整后端测试、Java 21 打包、前端测试/类型构建/lint 均须实际通过。浏览器端到端流程在独立本地验收环境执行，不能顺手覆盖未知运行中的 Compose 数据。实际云验收仍按 OSS 手册另行授权；这项权限变更不要求新增 OSS 权限，因为应用服务已拥有业务前缀读取/写入/删除权限，但实际云角色尚未验证，不能宣称已上线。
