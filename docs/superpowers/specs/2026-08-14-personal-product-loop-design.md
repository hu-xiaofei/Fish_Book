# FishBook 个人产品闭环设计规格

- 日期：2026-08-14
- 状态：设计已由用户逐节确认，等待书面规格复核
- 阶段：FishBook 第三阶段——个人收藏、钓获记录与可选照片
- 预计投入：5 周，每周约 10–15 小时
- 架构决策：按收藏、无照片钓获记录、可选照片、质量收口四个垂直切片推进

## 1. 背景与目标

FishBook 已经具备完整身份闭环、公开只读鱼类图鉴、MySQL/Flyway、同源 Docker 部署、CI 和 Playwright 端到端测试。当前用户可以注册、登录、浏览、搜索和筛选鱼类，但还不能把图鉴知识转化为自己的收藏和垂钓经验。

本阶段把 FishBook 从“可浏览的公共图鉴”推进为“可持续使用的个人鱼类知识与钓获记录工具”，形成以下闭环：

```text
浏览鱼类 → 收藏目标鱼 → 查看个人收藏 → 创建钓获记录
→ 可选上传照片 → 编辑或回顾记录 → 删除不再需要的记录
```

本阶段采用渐进式交付，每个里程碑都必须完成数据库、后端 API、前端页面、自动化测试和必要文档，不能先堆积多层未连通的半成品。

## 2. 范围与成功标准

### 2.1 本阶段包含

1. 登录用户收藏、取消收藏鱼类，并查看个人收藏列表。
2. 图鉴卡片和详情页显示当前用户的收藏状态。
3. 登录用户创建、查看、编辑和删除自己的钓获记录。
4. 钓获记录关联一个现有鱼种，包含日期、地点、长度、重量、钓法和备注。
5. 钓获记录可以不上传照片；记录创建后可以补传、替换或移除一张照片。
6. 照片保存到现有 MinIO，保持私有，并通过受权限保护的后端接口读取。
7. 所有收藏、钓获记录和照片严格按当前用户隔离。
8. 核心流程具有领域、应用、数据库、Web 安全、对象存储、前端和端到端测试。

### 2.2 本阶段不包含

- 管理员账号初始化、管理后台、鱼类新增、编辑、发布或下架。
- 收藏分类、标签、备注或公开分享。
- 多图相册、视频、图片编辑、压缩或自动内容识别。
- 钓获记录搜索、复杂筛选、统计仪表盘、地图、GPS、天气、水温或潮汐。
- 社区动态、关注、评论、点赞和通知。
- 公有云部署、自动生产发布和生产备份恢复演练。
- Redis、消息队列、微服务或独立媒体服务。

### 2.3 完成标准

本阶段完成时必须满足：

- 重复收藏不产生重复数据，重复取消收藏不报错。
- 用户只能看见自己的收藏、钓获记录和照片。
- 无照片也能完成钓获记录的创建、查看、编辑和删除。
- 图片上传失败不撤销或丢失已经保存的钓获记录。
- 用户能够补传、替换和移除照片。
- 支持的照片类型、大小和文件签名均在后端校验。
- 收藏与钓获核心流程通过真实浏览器端到端测试。
- 后端、前端、Docker Compose 和端到端验证全部通过。

## 3. 交付顺序与里程碑

### 3.1 里程碑一：个人收藏（第 1 周）

- 新增收藏表、唯一约束和查询索引。
- 实现幂等收藏、取消收藏和个人收藏分页查询。
- 在鱼类卡片、详情页和登录导航中接入收藏能力。
- 新增“我的收藏”页面。
- 完成用户隔离、幂等行为和真实浏览器流程测试。

出口条件：登录用户可以从图鉴收藏鱼类并在个人页面查看；重复操作不会产生脏数据；其他用户的收藏不可见。

### 3.2 里程碑二：无照片钓获记录（第 2–3 周）

- 新增钓获记录表、领域规则、Repository Port 和 JPA Adapter。
- 实现记录的创建、分页列表、详情、完整更新和删除。
- 实现列表、创建、详情和编辑页面。
- 完成输入边界、排序、所有权和越权测试。

出口条件：登录用户可以在不上传照片的情况下完成钓获记录 CRUD，并且不能读取或修改其他用户的数据。

### 3.3 里程碑三：可选照片与 MinIO（第 4 周）

- 新增独立 `media` 模块和 MinIO Adapter。
- 实现照片上传、读取、替换、移除和清理任务。
- 前端支持创建记录后补传照片，并在上传失败时保留记录主体。
- 完成格式伪装、大小超限、存储不可用和清理失败测试。

出口条件：用户可以为自己的记录管理一张私有照片；对象存储失败不会破坏记录主体；替换和删除不会造成用户可见的旧照片回退。

### 3.4 里程碑四：质量收口（第 5 周）

- 补齐端到端回归、错误状态和可访问性交互。
- 更新 README、API 约定、对象存储和故障处理文档。
- 执行完整后端、前端、容器和 Playwright 验证。

出口条件：本规格全部成功标准有自动化测试或书面验证证据，完整 CI 范围通过。

## 4. 架构与模块边界

系统继续采用现有 React SPA、Spring Boot 模块化单体、MySQL 和 MinIO，不增加独立服务。

```text
React
  → Favorites API → Favorites Application → Favorites Repository → MySQL
  → Catch Log API → Catch Log Application → Catch Repository → MySQL
  → Photo API     → Catch Log Application → Media Port → MinIO
                                           → Catch Repository → MySQL
```

后端新增三个模块：

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `favorites` | 收藏关系、幂等写入、个人收藏分页查询 | 修改鱼类资料、读取其他用户收藏 |
| `catchlog` | 钓获记录、所有权校验、记录与照片生命周期编排 | 解析 MinIO SDK、维护公共图鉴 |
| `media` | 文件校验、对象上传、读取、删除和清理重试 | 理解用户、鱼种或钓获业务 |

依赖方向继续遵守：

```text
Controller → Application Service → Domain / Repository Port → Infrastructure Adapter
```

约束：

- Controller 不直接访问 Spring Data Repository 或 MinIO Client。
- API 不返回 JPA Entity。
- `favorites` 和 `catchlog` 通过 Catalog 的公开查询能力确认鱼种存在，不直接访问 Catalog 的 Spring Data Repository。
- `media` 只接收对象键和经过边界校验的文件，不判断当前用户是否拥有钓获记录。
- 所有权校验和媒体生命周期由 `catchlog` 应用服务编排。

## 5. 数据模型

### 5.1 收藏

```text
favorites
- id              BIGINT 主键
- user_id         BIGINT，外键 users.id
- fish_species_id BIGINT，外键 fish_species.id
- created_at      DATETIME(6)
```

约束与索引：

- `UNIQUE(user_id, fish_species_id)` 保证同一用户只收藏一次同一鱼种。
- `(user_id, created_at, id)` 支持稳定的个人收藏倒序分页。
- 删除用户时级联删除其收藏；鱼种外键使用限制删除，避免个人引用被静默破坏。

### 5.2 钓获记录

```text
catch_records
- id               BIGINT 主键
- user_id          BIGINT，外键 users.id
- fish_species_id  BIGINT，外键 fish_species.id
- caught_on        DATE
- location         VARCHAR(200)
- length_cm        DECIMAL(8,2)，可空
- weight_g         DECIMAL(10,2)，可空
- method           VARCHAR(100)，可空
- notes            TEXT，可空
- photo_object_key VARCHAR(512)，可空
- created_at       DATETIME(6)
- updated_at       DATETIME(6)
```

约束与索引：

- `caught_on` 不得晚于应用按 `Asia/Shanghai` 业务时区认定的当前日期；应用使用可注入的 `Clock` 保证测试稳定。
- `length_cm`、`weight_g` 可空，但提供时必须大于或等于零。
- `location` 去除首尾空格后必须为 1–200 个字符。
- `method` 去除首尾空格后为空时保存为 `NULL`，否则最多 100 个字符。
- `notes` 去除首尾空格后为空时保存为 `NULL`，否则最多 5,000 个字符。
- `(user_id, caught_on DESC, created_at DESC, id DESC)` 支持稳定的个人列表排序。
- 用户和鱼种外键使用限制删除，避免数据库级联绕过媒体清理；账号删除不在本阶段实现，未来必须通过应用用例编排记录和照片清理。

### 5.3 媒体清理任务

```text
media_cleanup_jobs
- id              BIGINT 主键
- object_key      VARCHAR(512)
- reason          VARCHAR(50)
- status          VARCHAR(20)
- attempt_count   INT
- next_attempt_at DATETIME(6)，可空
- last_attempt_at DATETIME(6)，可空
- created_at      DATETIME(6)
```

替换、移除照片或删除带照片记录时，业务事务在更新主体数据的同时写入清理任务。`reason` 只允许 `REPLACED`、`REMOVED` 或 `RECORD_DELETED`，初始状态为 `PENDING`。Spring 定时任务分批删除对象；对象已经不存在视为成功并删除任务记录。失败任务从 1 分钟开始指数退避、最长间隔 24 小时，最多尝试 8 次。超过上限后状态改为 `FAILED`、清空下次执行时间并输出结构化错误日志，记录保留供人工排查。第一版不引入消息队列或独立任务服务。

## 6. 领域规则与应用流程

### 6.1 收藏与取消收藏

1. 从当前认证会话取得用户 ID。
2. 通过 Catalog 公开能力按 slug 确认鱼种存在。
3. 收藏时插入唯一关系；若关系已经存在，直接返回成功状态。
4. 取消时按当前用户 ID 和鱼种 ID 删除；若关系不存在，仍返回成功状态。
5. 收藏或取消成功后，前端使对应鱼类详情、目录和收藏列表缓存失效。

收藏 API 不接受客户端提供 `userId`。

### 6.2 创建钓获记录

1. 前端以 JSON 提交记录字段，不包含照片。
2. 后端取得当前用户 ID，校验鱼种与全部字段。
3. 后端保存无照片记录并返回记录 ID 和详情。
4. 若用户选择照片，前端随后调用独立照片接口。
5. 照片上传失败时，页面明确告知“记录已保存，照片未上传”，并提供重试入口。

记录主体和照片不使用一个 multipart 请求，避免对象存储失败回滚已经有效的文字记录。

### 6.3 补传或替换照片

1. 按记录 ID 和当前用户 ID 查询记录；不匹配时返回统一的资源不存在响应。
2. 校验声明的 MIME、实际文件签名、文件大小和允许类型。
3. 使用不可预测的 UUID 对象键上传新对象，对象键以用户和记录范围组织，但不能包含原始文件名。
4. 在数据库事务中更新记录的 `photo_object_key`；若存在旧对象，同时创建媒体清理任务。
5. 数据库事务失败时立即尽力删除刚上传的新对象；删除失败记录结构化错误日志。运维文档提供按对象键与数据库引用比对的孤儿对象排查步骤。

前端只在照片接口成功后更新照片展示；失败时继续展示原有照片或无照片状态。

### 6.4 移除照片和删除记录

- 移除照片：在同一数据库事务中清空 `photo_object_key` 并创建旧对象清理任务。
- 删除记录：按记录 ID 与当前用户 ID 删除；若存在照片，在同一事务中创建清理任务。
- 数据库提交后，记录或照片立即对用户不可见；对象物理删除由清理任务完成。
- 清理任务必须幂等，对不存在的对象执行删除视为成功。

### 6.5 读取照片

第一版使用后端受控读取，不返回永久公开 URL：

1. 后端按记录 ID 和当前用户 ID 校验所有权与照片存在性。
2. `media` 模块从 MinIO 读取对象流和 Content-Type。
3. 后端以安全的内联响应传输图片，并设置私有缓存策略。
4. 记录不存在、不属于当前用户或没有照片时均返回 `404 CATCH_PHOTO_NOT_FOUND`。

短时签名 URL 可以在后续性能需求出现时引入，不在本阶段预先实现。

## 7. HTTP API

所有写请求继续使用现有 Session Cookie 与 CSRF Token。除登录和 CSRF 获取方式外，以下接口全部要求认证。

### 7.1 收藏 API

```http
PUT    /api/v1/favorites/{fishSlug}
DELETE /api/v1/favorites/{fishSlug}
GET    /api/v1/favorites?page=0
GET    /api/v1/favorites/status?fishSlug=channa-argus&fishSlug=cyprinus-carpio
```

- PUT 和 DELETE 采用幂等语义，成功时返回 `204 No Content`。
- 收藏列表固定每页 12 条，不接受客户端 `size`。
- 默认按收藏时间倒序、ID 倒序排列。
- 列表条目复用 Catalog 的公开鱼类摘要字段，并包含 `favoritedAt`。
- 收藏状态接口供图鉴页面批量查询当前用户可见鱼类的状态，最多接受 12 个去重后的 slug，并返回每个输入 slug 的 `favorited` 布尔值；前端不得为列表中的每张卡片单独发起请求。

### 7.2 钓获记录 API

```http
POST   /api/v1/catches
GET    /api/v1/catches?page=0
GET    /api/v1/catches/{id}
PUT    /api/v1/catches/{id}
DELETE /api/v1/catches/{id}
```

- POST 接收 JSON，成功返回 `201 Created`、`Location` 和完整记录响应。
- PUT 表示完整更新可编辑的文字字段，不修改照片对象键。
- DELETE 成功返回 `204 No Content`，重复删除返回统一的记录不存在响应。
- 列表固定每页 20 条，不接受客户端 `size`。
- 默认按 `caughtOn DESC, createdAt DESC, id DESC` 排序。
- 响应包含鱼种 slug、中文名和必要的展示摘要，不要求前端为每一条记录额外查询鱼种详情。

创建与更新 JSON 字段：

```json
{
  "fishSlug": "channa-argus",
  "caughtOn": "2026-08-14",
  "location": "城郊水库",
  "lengthCm": 42.5,
  "weightG": 1350,
  "method": "路亚",
  "notes": "傍晚近岸中鱼"
}
```

### 7.3 照片 API

```http
PUT    /api/v1/catches/{id}/photo
GET    /api/v1/catches/{id}/photo
DELETE /api/v1/catches/{id}/photo
```

- PUT 使用 `multipart/form-data`，文件字段固定为 `photo`。
- 允许 JPEG、PNG、WebP，单张最大 10 MB。
- PUT 成功返回 `204 No Content`；存在旧照片时表示替换。
- DELETE 采用幂等语义：拥有记录但当前无照片时仍返回 `204 No Content`。
- GET 返回图片二进制流，且只允许记录所有者访问。

## 8. 前端设计

新增两个业务功能目录并复用现有共享 API Client、表单和认证能力：

```text
frontend/src/features/favorites
frontend/src/features/catchlog
```

### 8.1 路由与导航

```text
/favorites          我的收藏
/catches            我的钓获记录
/catches/new        创建钓获记录
/catches/{id}       钓获记录详情
/catches/{id}/edit  编辑钓获记录
```

全部路由使用现有受保护路由能力。登录后的顶部导航增加“我的收藏”和“钓获记录”；匿名用户点击收藏时跳转登录，并保留返回目标。

### 8.2 收藏交互

- 图鉴卡片和详情页显示收藏或已收藏状态。
- 操作期间禁用按钮，成功后同步目录、详情和收藏列表缓存。
- 服务端幂等语义是最终保障；前端不依赖乐观更新保证正确性。
- 收藏列表显式处理加载、空列表、请求失败、重试和分页状态。

### 8.3 钓获记录页面

- 列表页展示鱼种、日期、地点、尺寸摘要和照片缩略状态。
- 创建页先保存文字记录；成功后进入详情页并提供照片上传区域。
- 详情页展示全部字段和照片，并提供编辑、删除、补传、替换和移除入口。
- 编辑页只编辑文字字段；照片操作保留在详情页，减少多资源表单的失败组合。
- 删除操作要求用户确认，成功后返回列表并使相关缓存失效。

### 8.4 表单规则

前端使用 React Hook Form 和 Zod 提供即时反馈，但后端始终重新校验：

- `fishSlug` 必填，使用图鉴选项选择而不是自由输入。
- `caughtOn` 必填且不能晚于客户端今天；服务器日期是最终边界。
- `location` 必填，去除首尾空格后 1–200 个字符。
- `lengthCm` 和 `weightG` 可空，提供时大于或等于零。
- `method` 可空，最多 100 个字符。
- `notes` 可空，最多 5,000 个字符。

## 9. 安全与隐私

- 后端只从认证上下文获取当前用户，不接受任何收藏或钓获 API 中的客户端 `userId`。
- Repository 所有记录读取、更新和删除都同时限定记录 ID 与用户 ID。
- 访问其他用户的记录或照片与资源不存在使用相同 `404` 响应。
- 管理员角色不自动获得读取其他用户私人收藏、记录或照片的能力。
- MinIO Bucket 保持私有；对象键不作为授权凭据，也不直接暴露给前端。
- 后端同时校验 Content-Type、文件签名和大小；扩展名不作为信任依据。
- 对象键使用不可预测 UUID，原始文件名不进入对象键、日志或响应。
- 文件下载响应使用安全 Content-Type、`Content-Disposition: inline`、`X-Content-Type-Options: nosniff` 和私有缓存策略。
- 错误响应不得包含对象键、Bucket、数据库细节、堆栈或其他用户标识。

## 10. 错误处理

继续复用项目现有统一 JSON 错误结构，并新增稳定错误代码：

| 场景 | HTTP | 错误代码 |
| --- | --- | --- |
| 收藏鱼种不存在 | 404 | `FISH_NOT_FOUND` |
| 收藏状态查询参数非法或超过 12 个 slug | 400 | `INVALID_FAVORITE_QUERY` |
| 钓获输入不合法 | 400 | `INVALID_CATCH_RECORD` |
| 记录不存在或不属于当前用户 | 404 | `CATCH_RECORD_NOT_FOUND` |
| 照片不存在或不可访问 | 404 | `CATCH_PHOTO_NOT_FOUND` |
| 文件类型、签名或大小非法 | 400 | `INVALID_CATCH_PHOTO` |
| MinIO 暂时不可用 | 503 | `MEDIA_STORAGE_UNAVAILABLE` |

规则：

- 未登录继续使用现有安全错误响应；写请求缺少 CSRF Token 继续被拒绝。
- 图片上传失败不修改记录主体或现有照片引用。
- 媒体清理失败不回滚已经成功的记录更新或删除。
- 前端必须区分“记录未保存”和“记录已保存但照片未上传”，不能用一个笼统错误提示覆盖二者。
- 未预料异常返回安全的 `500`，服务端通过结构化日志记录请求上下文，但不记录照片内容或私人备注正文。

## 11. 测试策略

### 11.1 后端领域与应用测试

- 收藏、重复收藏、取消和重复取消的幂等行为。
- 钓获日期、地点长度、可空字段、数值下限和文本长度边界。
- 当前用户所有权判断和统一不存在行为。
- 创建、更新、删除与媒体清理任务编排。

### 11.2 真实数据库与迁移测试

- Flyway 在空 MySQL 上完整迁移。
- 收藏唯一约束、外键和稳定分页排序。
- 钓获记录分页排序、用户隔离和所有权限定查询。
- 替换、移除照片和删除记录时，主体变更与清理任务在同一事务提交。

### 11.3 Web 与安全测试

- 匿名访问所有个人接口被拒绝。
- 缺少或错误 CSRF Token 的写请求被拒绝。
- 用户不能读取、修改、删除其他用户的收藏、记录和照片。
- PUT、DELETE 的幂等或不存在语义符合本规格。
- 错误响应不泄露内部信息。

### 11.4 MinIO 集成测试

- 合法 JPEG、PNG、WebP 上传和受控读取。
- 声明 MIME 与文件签名不一致、格式不支持和超过 10 MB 的拒绝路径。
- 补传、替换、移除和对象已不存在时的幂等清理。
- MinIO 不可用时返回稳定 `503`，记录主体和旧照片引用不变。
- 清理失败任务保留并按退避规则重试。

### 11.5 前端测试

- 图鉴卡片、详情和收藏列表之间的收藏状态同步。
- 匿名收藏跳转登录及返回目标。
- 钓获表单校验、空列表、加载、请求失败和重试。
- 创建成功后照片上传失败的分离提示与重试入口。
- 详情、编辑、删除、照片补传、替换和移除交互。

### 11.6 端到端测试

Playwright 至少覆盖：

1. 注册或登录 → 搜索鱼类 → 收藏 → 查看个人收藏 → 取消收藏。
2. 创建无照片钓获记录 → 查看详情 → 编辑 → 删除。
3. 创建记录 → 补传照片 → 替换或移除照片。
4. 第二个用户无法通过直接 URL 或 API 读取第一个用户的记录和照片。

质量收口阶段更新：

## 13. 主要风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 收藏、记录和照片同时开发导致范围失控 | 四个垂直切片按出口条件依次交付，不并行铺开半成品 |
| 用户可通过猜测 ID 越权访问私人数据 | 所有 Repository 查询同时限定资源 ID 与当前用户 ID，并覆盖安全测试 |
| 照片失败导致整条记录丢失 | 记录 JSON 与照片使用两个独立请求，先保存记录主体 |
| 替换或删除照片产生孤儿对象 | 数据库清理任务、幂等删除、重试和运维排查步骤 |
| 伪造文件导致安全问题 | 同时校验声明 MIME、文件签名、允许类型和大小，Bucket 保持私有 |
| 过早加入统计、地图或社区能力 | 严格执行非范围列表，完成个人闭环后再评估新需求 |
